# Catalogue Sync

The site's browsable card catalogue is a **live, server-cached view of PokeTrace's own `/sets` and `/cards` endpoints** — not a static file. There is no `src/data/sets.js`, no `src/data/cards.json`, no `scripts/build-card-db.js` anymore, and no "sync" or "rebuild" step to run. Sets are keyed by PokeTrace's own `slug`; cards by PokeTrace's own `id` (uuid); card images come from PokeTrace's own `Card.image` field. If a set exists in PokeTrace's catalogue, it exists in the site's catalogue — always, automatically, because they're the same request. **Don't reintroduce a static bundle or a GitHub cross-reference for what sets/cards exist** — that's the exact setup this replaced (see git history around "re-key catalogue onto PokeTrace" for the full rationale).

One deliberate exception: **set-level `releaseDate`, `series` (era), and logo image are enriched from pokemontcg.io**, not PokeTrace — see "Era grouping" below. This is read-only display metadata layered on top of PokeTrace's set list, not a second source of truth for what exists.

## Where it lives

- **`server.js`**: `GET /api/sets?game=pokemon|pokemon-japanese` (paginates PokeTrace's `/sets`, then enriches English results with pokemontcg.io metadata, 24h in-memory cache), `GET /api/sets/:slug/cards` (paginates `/cards?set=<slug>`, 24h cache), `GET /api/cards/search?name=&number=` (thin proxy to `/cards?search=`, used by CSV import when a row's set name doesn't resolve to a slug). All three route through the shared `pokeTraceFetch` queue like every other PokeTrace call in this file. `getPokemonTcgIoSetsByName()` / `fetchPokemonTcgIoSets()` do the pokemontcg.io side — separately cached (24h on success, 5min on failure so a flaky moment doesn't strand the catalogue without era data for a full day).
- **`src/api/poketrace.js`**: `fetchSets(game)`, `fetchSetCards(slug)`, `searchCards(name, number)` — thin `apiGet` wrappers around the routes above. `TCG_CDN` (`images.pokemontcg.io`) is still exported and still used, but only as a fallback in `Portfolio.jsx`'s `getCardImage()` for pre-migration rows that don't have a stored `image` — don't read that as "the CDN is still part of the catalogue," it's legacy-row-rendering only.
- **`src/data/eraMap.js`**: `ERA_MAP` (series name → `{key, label, color}`) and `getEra(series)`. Keyed on pokemontcg.io's `series` string, which is only present on a set when the server successfully matched it by name (see below) — anything else falls into the `{key:'other', label:'Other Sets'}` bucket. This is a small, fixed, hand-written table (era boundaries/colors don't change), not catalogue data that drifts — same category as `editions.js` below, not a reintroduction of the removed static bundle.
- **`src/pages/Catalogue.jsx`**: fetches the set list on mount/language-switch, groups by era (`eraOrder`/`grouped`, most-recent-era-first, "Other Sets" last, sets within each era sorted by `releaseDate` descending), fetches one set's cards on open. No static import of set/card data anywhere in this file.
- **`src/utils/csvImport.js`**: `matchCard(row, cards)` takes a flat array of already-fetched PokeTrace cards (normalized via `normalizeApiCard` in `Portfolio.jsx`) — no local database to scan.
- **`src/data/editions.js`**: `EDITION_ELIGIBLE_SET_NAMES`, a fixed 10-entry historical fact table (which WotC-era sets actually shipped with a 1st Edition print run), keyed by set **name**. Don't try to derive it from a date range (Base Set 2, Legendary Collection, Wizards Black Star Promos, and the E-Card sets are chronologically inside the WotC window but were never 1st-Edition-stamped).

## Era grouping, release dates, and set logos — sourced from pokemontcg.io, not PokeTrace

PokeTrace's `Set` object is `{slug, name, cardCount}` only — confirmed live, `releaseDate` is `null` on every one of its ~502 `game=pokemon` entries, and there's no series/era or logo field at all. None of "sort by release date," "filter by era," or "show a set logo" can be built from PokeTrace alone.

The fix: `server.js`'s `/api/sets` route (English only — pokemontcg.io's public set list has no Japanese sets) fetches `https://api.pokemontcg.io/v2/sets` once (cached), builds a `normalizeSetName(name) → {releaseDate, series, logo}` map, and merges it onto each PokeTrace set that matches by normalized name. This works for the ~177 of PokeTrace's ~502 English entries whose name matches a real pokemontcg.io set exactly — the rest (near-duplicate/sealed-product slugs, see below) get no era/date/logo and fall into "Other Sets", sorted alphabetically, with a placeholder badge instead of a logo. That's expected, not a bug — don't try to improve the match rate with fuzzy/partial name matching; it'll misattribute logos/dates to the wrong slug given how many near-duplicates PokeTrace has for the same real set name.

`ERA_MAP` in `eraMap.js` is keyed on pokemontcg.io's exact `series` strings, which have a couple of quirks vs. the display labels: `'HeartGold & SoulSilver'` (with an ampersand) and a separate `'Platinum'` series (folded into the `dp`/"Diamond & Pearl" bucket to match how this app has always grouped it) — don't "fix" these into what looks like a typo, they're intentional.

## Real gotchas found by hitting the live APIs (not in either's docs)

These cost real debugging time — add them to `poketrace-api-expert`'s reference too if that skill is touched again.

- **PokeTrace's `Set.releaseDate` is always `null`, and there's no series/logo field at all** — see "Era grouping" above for the workaround now in place. If that enrichment is ever removed, era filters/date-sort/logos have no data source and will need to be dropped again, not faked.
- **pokemontcg.io's API (`api.pokemontcg.io`) intermittently 500s under completely normal load, recovering seconds later** — confirmed by hand, hitting it a handful of times in a row produced 500, 500, 500, 200. This was already known and documented above `fetchPokemonTcgIoPrice` in `server.js` (the pricing fallback) before this enrichment existed; `fetchPokemonTcgIoSets` uses the same retry pattern (3 attempts, backoff) for the same reason. Any new pokemontcg.io call needs the same retry discipline — don't add a bare `fetch` to it.
- **A hard `market=US` filter on `/cards?set=<slug>` silently returns zero results for a real subset of sets**, even when `/sets` reports a nonzero `cardCount` for that exact slug. Confirmed live: `set=destined-rivals` (cardCount 410) returns **0** rows under `market=US` but 410 under no market filter — the entire set is EU/Cardmarket-sourced on PokeTrace's side. Don't add a `market` filter to `/api/sets/:slug/cards` or `/api/cards/search`; fetch across all markets and dedupe instead (see `dedupeCards()` in `server.js` — keys on `cardNumber|name`, prefers a `market:'US'` entry over others when both exist for the same card).
- **PokeTrace's catalogue has many more "sets" than pokemontcg.io's curated one, including near-duplicate entries for the same real-world release.** E.g. searching "Destined Rivals" returns three separate PokeTrace slugs — `destined-rivals` (410 cards, EU-sourced), `destined-rivals-additionals` (44 cards), `sv10-destined-rivals` (281 cards, US-sourced) — for what a collector would call one set, and pokemontcg.io's name-matching only cleanly hits one of the three (`destined-rivals`, since its name is the exact bare match). Don't try to collapse or curate these into one canonical entry — that reintroduces exactly the kind of hand-maintained mapping this whole effort moved away from. The set-name search box in `Catalogue.jsx` exists specifically to make this navigable; the era/date/logo gap on the other two is accepted, not a bug to chase.

## If asked to "check the catalogue is current"

It always is — say so, and explain why (live proxy, no static file, no rebuild step). There's nothing to audit or diff. If the *complaint* is that browsing feels incomplete, a set looks empty, or a set has no logo/era/date, the likely cause is one of the gotchas above (an EU-only slug, the near-duplicate-slugs situation, or a pokemontcg.io name-match miss), not staleness — check those before assuming something's broken.
